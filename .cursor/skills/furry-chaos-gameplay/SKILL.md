# FurryChaos Gameplay 开发规范

## 目标

在扩展项目时同时守住三件事：

1. 玩法始终服务于“多人合作产生欢乐与搞怪场面”。
2. 局内遵循“搜集/执行任务 → 应对风险与追逐 → 撤离”的搜跑撤循环。
3. 代码遵循服务端权威、职责分层、数据驱动、可组合和可验证原则。

本规范描述目标边界，不代表所有能力已实现。先检查现有代码、Prefab、场景和配置，再判断是复用、补齐还是新建；不得根据本规范臆测 API 已存在。

## 使用流程

处理 Gameplay 需求时按以下顺序执行：

1. 明确需求属于局外、流程、局内规则、表现或基础设施中的哪一层。
2. 检查相关源码和资源，画清生命周期、服务端/客户端职责、状态拥有者及数据流。
3. 用一句话说明该功能如何强化合作、搞怪或搜跑撤循环；无法说明时，先质疑其必要性。
4. 优先扩展现有系统和接口，避免创建平行管理器、全局单例或第二套交互/道具框架。
5. 先设计权威状态和验证规则，再设计 RPC、客户端预测、动画、音效和 UI。
6. 将可调数值放入配置，将运行时状态留在局内实例，不把二者混在 ScriptableObject 中。
7. 完成后检查 Host、Client、晚加入/重连、重复请求、玩家中途离开和局内清理。

若需求会改变核心循环、胜负/撤离规则、玩家人数、敌我关系、永久成长或世界设定，不自行定案；列出影响并向用户确认。

## 游戏世界与体验支柱

### 固定方向

- 这是轻松欢乐、允许失误和互相坑害但鼓励合作的多人联机游戏。
- 玩家共同进入局内，在环境压力和狗狗威胁下完成任务并尝试撤离。
- 当前主要敌对 AI 是狗狗；已实现范围仅包括巡逻、发现/追逐和攻击等基础行为。
- 任务可要求玩家在特定地点对狗粮或其他任务道具进行拾取、携带、转移、放置、加工或交付。
- 玩家可从局外带入增益道具，也可使用局内生成的消耗品、工具、伪装或任务物品。
- 搞怪来自可读规则下的物理互动、误操作、追逐、救场和角色分工，不依赖恶意惩罚、强制内斗或纯随机失败。

### 设计检查

新增机制至少满足以下一项，最好形成组合：

- 促使玩家分工、接力、掩护、诱敌、救援或共享信息。
- 产生其他玩家能看懂并参与的意外场面。
- 为“继续搜/做任务”与“及时撤离”制造风险收益选择。
- 允许失败后补救，形成故事，而不是立即剥夺长时间参与权。
- 与任务、道具、狗狗 AI、环境或队友产生系统性交互。

避免：

- 只有数值增长、没有新决策或团队互动的功能。
- 单人即可无视队友稳定完成的核心任务。
- 客户端自行判定任务完成、获得道具、命中、伤害或撤离成功。
- 用不可读的随机事件直接清空进度。
- 在欢乐定位下引入写实血腥、沉重残酷或永久伤害，除非用户明确改变方向。

## 核心循环

### 局外

`组队/大厅 → 选择携带物与增益 → 准备 → 进入局内`

- 局外配置只描述本局初始携带内容，不直接修改局内权威状态。
- 带入物应提供策略和搞怪组合，不应形成无法匹配的硬性战力门槛。
- 大厅准备、选角和携带物必须在开局前由服务端生成可信快照。

### 局内

`生成 → 探索搜集 → 执行多阶段任务 → 遭遇/规避狗狗 → 整理收益 → 选择撤离`

- 任务推进与资源搜集应让队伍在移动、噪声、负重、时间和风险之间取舍。
- 狗狗是持续施压者，不只是伤害来源；优先扩展感知、调查、失去目标、声音诱导和群体应对。
- 倒地、掉落、噪声、误触发或失败宜提供队友救场空间。
- 撤离必须是服务端判定的明确阶段，并定义参与玩家、携带物结算和失败条件。

### 结算

`撤离/失败 → 服务端形成结算快照 → 局外奖励与消耗结算 → 返回大厅`

- 结算只读取服务端最终状态。
- 区分任务成功、个人是否撤离、物品是否带出和队伍奖励。
- 网络断开、Host 退出和重复结算必须幂等处理。

## 当前框架事实

以代码为最终依据；修改前重点查看：

- `Assets/Scripts/Core/GameRoot.cs`：顶层系统注册、生命周期和更新入口。
- `Assets/Scripts/Core/Base/System/`：`ISystem`、`LogicSystem`、`SubSystem` 及各领域系统。
- `Assets/Scripts/Core/Base/System/GameFlowSystem/`：登录、大厅、加载、局内、结算流程。
- `Assets/Scripts/Core/Base/System/GamePlaySystem/`：Gameplay 领域系统骨架。
- `Assets/Scripts/Core/Base/System/NetSystem/`：NGO 网络启动、连接和网络场景加载。
- `Assets/Scripts/GameLogic/Common/Interact/`：交互接口、基础类和探测器。
- `Assets/Scripts/GameLogic/Item/`：道具数据、实例、效果和背包相关逻辑。
- `Assets/Scripts/GameLogic/Furry/Cat/`：玩家角色、输入、移动与网络实体。
- `Assets/Scripts/GameLogic/Furry/Dog/`：狗狗感知、导航、战斗和 Behavior Designer 节点。

项目使用 Unity 2022.3、Unity Netcode for GameObjects、UniTask、Addressables、Behavior Designer、Animancer、Kinematic Character Controller、Odin Inspector、Steamworks/Dissonance 等。先复用已安装能力，不随意引入同类依赖。

`GamePlaySystem` 当前是未完成骨架；依赖它之前确认它已由 `GameRoot` 注册并正确参与生命周期。任务系统、撤离系统等规范属于目标架构，不得假装现有实现已经完成。

## 分层与目录

### 系统职责

- `GameRoot`：只负责顶层系统组装和生命周期转发，不承载具体玩法规则。
- `LogicSystem`：一个稳定领域的顶层服务，如流程、网络、加载、UI、Gameplay。
- `SubSystem`：隶属于某个 `LogicSystem` 的领域模块，由主系统创建、初始化、更新和释放。
- `GameFlowSystem`：管理 Login/Lobby/Loading/InGame/Result 等跨场景阶段，不处理具体任务目标。
- `GamePlaySystem`：承载局内规则编排；目标子系统包括 Task、Interaction、Item、Inventory、Extraction、Spawn 等。
- `NetworkBehaviour`：网络实体或局内权威状态边界，不应成为查找所有系统的万能控制器。
- `MonoBehaviour`：场景/Prefab 组件、表现适配或本地探测，不拥有跨局核心状态。
- `ScriptableObject`：静态配置和内容定义，不保存会在多人局中变化的运行时状态。

### 放置规则

- 通用框架与生命周期放在 `Assets/Scripts/Core/`。
- 具体玩法组件放在 `Assets/Scripts/GameLogic/` 对应领域。
- 编辑器工具只放在 `Assets/Scripts/Editor/`。
- 第三方目录、插件源码和导入包不做顺手修改。
- 一个功能按领域组织，不按 `Managers`、`Utils`、`Misc` 等模糊类别堆放。
- 新增同类文件时沿用附近目录和命名；大规模目录或命名空间迁移必须单独规划。

依赖方向为：

`表现/UI → Gameplay 公共查询或事件 → 领域系统 → 网络/加载等基础设施`

不要让 Core 依赖具体 UI，不要让任务规则直接操作 UI 控件，不要让道具效果直接查找场景中的任意对象。

## 多人联机规则

### 权威边界

服务端唯一决定：

- 任务状态、目标计数、任务物品归属及完成/失败。
- 道具生成、拾取、丢弃、转移、消耗和效果生效。
- 背包容量、重量、局外带入物是否合法。
- 狗狗感知、选目标、导航、攻击、命中和伤害结果。
- 出生、撤离资格、局内计时、结算和奖励快照。

客户端负责：

- 采集本地输入并发送“意图”。
- 可安全预测的本地移动与即时反馈。
- 根据复制状态播放动画、音效、特效和 UI。

### RPC 与状态同步

- RPC 表达意图或一次性通知；持续状态使用 `NetworkVariable`、`NetworkList` 或可供晚加入者重建的网络对象。
- 任何客户端请求都在服务端验证：调用者身份、距离、阶段、对象状态、权限、冷却、容量和重复提交。
- 不信任客户端传入的价格、伤害、完成标记、物品配置或目标结果；客户端尽量只传对象 ID 和操作意图。
- 可被重复发送的请求必须幂等；用状态、唯一交互 ID 或序列号拒绝重复处理。
- 可靠传输用于关键离散事件；高频输入/快照可用不可靠传输，并容忍丢包和乱序。
- 订阅 NGO/Unity 事件后，在 `OnNetworkDespawn`、`OnDisable` 或 `OnDispose` 的对称位置取消订阅。
- 逻辑必须兼容 Host 同时是服务端和客户端，避免 Host 重复执行表现或结算。
- 服务端代码不得依赖相机、本地输入或 UI；`UNITY_SERVER` 下应能运行。

沿用项目当前 NGO 版本的 `[ServerRpc]`/`[ClientRpc]` 风格；除非统一升级依赖，不混入其他版本 API。

## Gameplay 领域设计

### 任务系统

新增任务框架时拆分为：

- `TaskDefinition`：ScriptableObject 静态定义，含稳定 ID、目标定义、阶段关系和可调参数。
- `TaskSystem`：`GamePlaySystem` 的子系统，服务端创建、推进、失败和结束任务。
- `TaskRuntime`：本局权威状态；不写回 Definition。
- `TaskObjective`：可组合目标，如拾取、携带、放置、交付、区域交互、计时或多人协作。
- `TaskView`/UI：只读取复制后的摘要或监听事件，不参与完成判定。

任务状态至少清晰区分 `Inactive`、`Active`、`Completed`、`Failed`；多阶段任务只允许服务端推进。使用稳定 ID 关联配置，不用显示名称、Hierarchy 路径或数组下标充当持久标识。

优先组合小目标，不为每个任务复制整套控制器。目标要定义：

- 激活条件、完成条件和失败条件。
- 玩家离开、物品销毁/掉落、目标重复交互时的行为。
- 是否需要多人同时/依次协作。
- 对晚加入客户端公开的最小状态。

### 交互

- `InteractionDetector` 只负责本地候选检测和提示；最终交互必须发送到服务端验证。
- `IInteractable` 描述能力，不把具体任务逻辑硬编码进探测器。
- 交互需支持按下/长按、占用、取消、中断和不可用原因的扩展。
- 任务物品转移应通过明确的持有者/容器状态完成，不能只修改 Transform 父子关系。
- 提示文本与真实可交互状态来自同一份状态，但 UI 不应每帧触发网络请求。

### 道具、背包与效果

- `ItemData` 保存静态定义；`Item`/`BagItemEntity` 保存本局实例状态。
- 局外带入、局内生成、任务物品和可带出收益使用明确来源/标签区分。
- 效果由服务端应用；客户端只播放反馈。持续效果必须定义叠加、刷新、互斥、移除和断线行为。
- 容量、重量、消耗和转移应通过统一领域 API 修改，禁止多处直接写网络变量。
- 任务物品默认不可被普通消耗逻辑销毁，除非任务规则明确允许。

### 狗狗 AI

- AI 决策和 NavMesh 驱动只在服务端运行，客户端消费同步状态并播放表现。
- 保持感知、决策、导航、战斗、动画分离；Behavior Designer Action/Condition 节点保持单一职责。
- 当前基础链路是巡逻 → 发现 → 追逐 → 攻击；新增调查声源、搜索最后位置、受诱饵影响、眩晕或丢失目标时，作为可组合状态/节点扩展。
- 目标选择需稳定且可解释，考虑距离、可见性、噪声、威胁与有效性，不在每帧无条件全场扫描。
- 攻击命中由服务端判定；动画事件可决定表现时机，不能成为客户端权威结果。

## C# 与 Unity 命名规范

- 类型、枚举、方法、属性、事件：`PascalCase`。
- 接口以 `I` 开头，如 `IInteractable`；抽象基类按职责使用 `Base` 后缀。
- 私有字段使用 `m_CamelCase`，包括 `[SerializeField]` 字段；不要新增无前缀的私有字段。
- 方法参数和局部变量使用 `camelCase`。
- 布尔值使用 `Is`、`Has`、`Can`、`Should` 前缀；集合使用复数名。
- 异步可等待方法使用 `Async` 后缀；刻意不等待的 `UniTaskVoid` 入口也应表达用途并处理异常/取消。
- NGO RPC 保留 `ServerRpc`/`ClientRpc` 后缀；服务端专用普通方法使用 `Server` 前缀时保持领域内一致。
- 配置类型使用 `Definition`、`Data` 或 `Profile` 中最贴切的一个；运行时类型使用 `Runtime`、`State`、`Session` 或 `Entity`，不要混称。
- 文件名与主类型名一致；每个文件通常只放一个主类型。
- 常量使用 `PascalCase`；避免散落魔法数，将可调值放入序列化配置。

成员可见性规则：

- 默认 `private`；只有稳定 API 才设为 `public`。
- Inspector 字段优先 `[SerializeField] private` 加只读属性，不新增可任意写入的 public 字段。
- 集合对外暴露只读视图或领域方法，不返回可修改的内部 `List`。
- 事件用动词后的事实命名，如 `TaskCompleted`、`ItemTransferred`；事件处理方法使用 `OnTaskCompleted`。

项目现有序列化 MonoBehaviour 大多位于全局命名空间。不要零散迁移命名空间，以免破坏 Unity 序列化和引用；若要引入命名空间，先制定完整迁移方案。

## 编码与生命周期约束

- `MonoBehaviour`/`NetworkBehaviour` 不使用构造函数注入；在 `Awake` 获取本地组件，在 `OnNetworkSpawn` 初始化网络职责。
- 系统依赖在 `OnInit`/`OnAfterAllSystemInit` 建立，在 `OnDispose` 清理；子系统必须由主系统持有并参与生命周期。
- 不在 `Update` 中使用 `Find`、LINQ、分配型物理查询或频繁创建集合；复用缓存和 NonAlloc API。
- 所有事件订阅、CancellationTokenSource、计时器和异步任务都有明确所有者和释放点。
- `async void` 仅用于 Unity 事件入口；业务异步使用 `UniTask`，支持取消并显式处理异常。
- 关键失败使用项目日志系统并带稳定 Tag；不要用日志代替状态处理，也不要提交高频逐帧日志。
- 修改序列化字段名时使用 `FormerlySerializedAs`；删除/移动组件前检查 Prefab 和场景引用。
- 不手工编辑 Unity 生成的 `.meta` GUID；创建资源后保持对应 `.meta` 纳入版本控制。
- 不顺手重构无关代码，不覆盖用户未提交的场景或 ProjectSettings 修改。

## 完成标准

提交 Gameplay 变更前至少验证：

- [ ] 功能强化合作、搞怪或搜跑撤循环，且没有偏离欢乐定位。
- [ ] 权威状态只有一个拥有者，客户端请求均经过服务端验证。
- [ ] Host 与至少一个 Client 的结果一致，没有 Host 双执行。
- [ ] 晚加入者可从持续状态恢复，不依赖错过的 ClientRpc。
- [ ] 重复交互、断线、对象销毁、场景切换和玩家离开有明确结果。
- [ ] UI/动画与规则解耦，专用服务端不会访问本地表现组件。
- [ ] 配置与运行时状态分离，没有把局内状态写回 ScriptableObject。
- [ ] 生命周期订阅和资源得到清理，没有明显每帧分配。
- [ ] 保留现有序列化数据和网络兼容性，或明确提供迁移方案。
- [ ] 相关测试、编译和静态检查通过；无法运行 Unity 验证时明确说明未验证部分。

向用户汇报时简洁说明：实现内容、权威/同步方案、对核心循环的作用、验证结果和仍需在 Unity 中配置的 Prefab/场景步骤。
